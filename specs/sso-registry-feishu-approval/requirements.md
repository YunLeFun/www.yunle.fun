# SSO Client Registry 飞书审批需求

状态：Confirmed（2026-09-04）

阶段：P1.2（生产审批交互与管理员身份关联）

涉及仓库：`YunLeFun/www.yunle.fun`、`YunLeFun/admin`

前置阶段：`../sso-client-registry-static-release/`

## 1. 背景与目标

现有 production Registry 发布与回滚使用邮件验证码审批，安全边界完整，但操作链路较长。P1.2 在不改变 Registry 权威事务、静态产物裁决和 CI 部署模型的前提下，引入飞书私聊审批卡片，并允许管理员在 Admin 中关联自己的飞书账号。

目标是让飞书成为首选审批交互通道，邮件成为可用性降级通道；任何通道都只能表达管理员意图，最终审批消费、快照、发布意图和审计仍由 SSO Provider 原子裁决。

## 2. 已确认边界

### 2.1 Admin 负责人机交互

`admin.yunle.fun` 负责：

- 飞书账号关联、换绑与解绑
- 审批卡片发送、有限重试和状态更新
- 飞书回调验签、租户与身份匹配
- 审批详情与账号连接设置页面
- 每次操作时重新校验管理员状态、权限和绑定
- 向 Provider 签发短时、单次用途的审批证明
- 用户主动切换到邮件审批

### 2.2 Provider 负责权威事务

`www.yunle.fun` 负责：

- Registry 草稿、差异、哈希和审批记录
- 审批有效期、证据绑定与一次性消费
- 校验 Admin 签发的审批证明
- 原子创建或确认快照、发布意图、outbox 与审计
- 邮件验证码的生成、MAC、校验和消费
- CI、部署回执、回滚和最终状态

Admin 不直接读写 Registry 集合；Provider 不解析飞书回调，也不保存飞书 OAuth token。两个系统之间只交换最小审批标识、展示所需只读数据和短时签名证明。

## 3. 非目标

- 不建设通用审批流、通知平台或多级会签引擎。
- 不改变 Registry generated JSON 作为线上唯一授权裁决源的模型。
- 不允许飞书直接调用 CI、修改 Registry 或绕过 Provider 事务。
- 不在本阶段提供完整的管理员绑定管理后台；只支持管理员管理自己的连接。
- 不通过群聊、公开卡片或邮件 GET 链接完成审批。
- 不存储飞书手机号、邮箱、头像或 OAuth token 作为授权依据。
- 不恢复 development 环境；灰度与验证直接在 production 以受控功能开关进行。

## 4. 功能与安全需求

### R1. 飞书身份关联

管理员必须从 Admin 的“设置 / 账号连接”发起飞书 OAuth 关联。关联、换绑和解绑必须经过现有 GitHub numeric ID 高风险二次确认。

系统必须使用独立的 server-only `admin_identity_bindings` 数据集合，至少保存 Admin uid、provider、tenant key、open id、可选 union id、展示名快照和时间戳。每个 Admin 账号和每个飞书身份同一时间最多存在一个有效绑定；冲突必须失败关闭并记录安全审计。

### R2. 授权与权限

身份关联不等于审批授权。Registry 审批必须使用显式权限 `sso-registry:approve`：owner 隐式拥有；普通 admin 只有被明确授予时才拥有，不得因 admin 角色自动获得。

每次点击批准、拒绝或切换邮件时，Admin 必须重新读取并校验管理员为启用状态、权限仍有效、飞书绑定仍有效、tenant key 与 open id 精确匹配、审批未过期且未终结。任何检查异常必须失败关闭。

### R3. 卡片投递与内容

production 发布和常规回滚都必须支持向预先指定的单一审批者发送飞书私聊卡片。卡片至少展示环境、操作类型、策略版本、客户端数量、变更摘要、申请人、原因、过期时间以及截断后的内容哈希和安全哈希，并提供 Admin 只读详情入口。

卡片不得包含审批秘密、完整签名、凭据或完整 Registry 正文。含安全字段变化或移除的操作必须使用明显的危险提示，并在批准时触发飞书原生确认。

### R4. 投递可靠性与邮件降级

卡片发送必须使用稳定幂等键，并进行最多 3 次短退避重试。仅在投递明确失败或重试耗尽时，系统才自动启用邮件审批；卡片投递成功时不得同时发送邮件。

当卡片已送达但不可用时，审批者必须能在 Admin 主动切换到邮件审批。邮件验证码只在降级实际启用时生成，并继续遵循现有 30 分钟有效、单次消费、失败次数限制和服务端 MAC 规则。

### R5. 飞书回调与一次性操作

Admin 必须验证飞书回调签名、防重放字段、允许的 tenant key 和绑定的 open id。验证通过后应快速、幂等地持久化一次操作并返回；权威审批事务异步完成，卡片先显示“处理中”，随后更新为最终状态。

重复点击、重复回调、过期卡片、已撤销绑定或已终结审批不得产生第二次发布、回滚或邮件降级。

### R6. Admin 审批证明

Admin 只能在 R2 和 R5 全部通过后签发短时 Ed25519 审批证明。证明必须绑定审批 ID、动作、Admin uid、飞书身份摘要、签发时间、到期时间、唯一标识和所需 Registry 证据，不得承载可由调用方替换的 Registry 正文。

Provider 必须校验固定 issuer、audience、action、可信公钥、短有效期、唯一标识、审批证据和允许的 Admin approver uid；验证异常时不得消费审批或创建发布意图。

### R7. Provider 原子裁决

Provider 收到合法证明后，必须在事务内重新读取审批与 Registry 证据，确认环境、操作、草稿或历史快照、base、content hash、security hash、有效期和未消费状态完全匹配，然后一次性消费审批并创建或确认不可变快照、发布意图、outbox 和审计。

批准、拒绝、邮件降级、发布和回滚必须可按 approvalId 与 releaseIntentId 追踪。拒绝必须原子终结当前审批，并使卡片与邮件路径同时失效；再次发布必须创建新审批。

### R8. 解绑、撤权与故障隔离

解绑飞书、停用管理员或撤销 `sso-registry:approve` 后，所有尚未权威消费的卡片操作必须立即失效。已完成的审计记录不得删除或改写。

飞书或 Admin 不可用不得降低 Registry、CI 或授权运行时安全性。Provider 保留独立邮件降级能力；任何外部调用失败都不得在不确定状态下自动批准。

### R9. 兼容性与发布策略

本阶段采用增量接口与新集合，不修改现有客户端 Registry schema、SSO 协议或 generated JSON 格式，不要求 breaking version，也不迁移历史审批记录。

功能必须由 production 开关控制：先仅向 owner 开放，对零安全差异变更完成卡片发送、批准、拒绝、重放、过期和邮件降级演练；验证通过后再默认启用。关闭开关时，现有邮件审批流程必须继续可用。

## 5. EARS 验收标准

1. 当启用的管理员完成 GitHub 二次确认并关联允许租户内的飞书账号时，系统应建立唯一有效绑定并记录安全审计。
2. 当管理员没有显式 `sso-registry:approve` 权限时，即使已关联飞书，系统也应拒绝其审批操作。
3. 当 production 发布或常规回滚请求满足条件时，系统应只向指定审批者私聊发送一张内容受限的审批卡片。
4. 当卡片成功投递时，系统不应生成或发送邮件验证码。
5. 当卡片明确投递失败、3 次重试耗尽或审批者主动切换通道时，Provider 应创建新的邮件验证码并启用现有邮件审批路径。
6. 当飞书回调的签名、租户、open id、管理员状态、权限、绑定或有效期任一无效时，Admin 应拒绝签发审批证明。
7. 当同一合法回调被重复投递或重复点击时，系统应返回同一处理结果，且最多产生一次 Provider 权威事务。
8. 当 Provider 收到合法短时证明时，系统应重新核对全部 Registry 证据，并原子消费审批、创建或确认发布意图与审计。
9. 当证明被篡改、过期、重放、issuer 或 audience 不匹配、approver uid 不允许或 Registry 证据已变化时，Provider 应失败关闭且不得排队发布。
10. 当审批者拒绝操作时，Provider 应原子终结审批，并使同一审批的卡片和邮件操作都不可继续使用。
11. 当管理员解绑、被停用或被撤权后再点击旧卡片时，系统应拒绝操作；既有审计仍应保留。
12. 当功能开关关闭或飞书通道不可用时，现有邮件审批、Registry 静态裁决和 CI 部署路径应保持可用且行为不变。
13. 当功能完成 production canary 时，发布、回滚、拒绝、重放、过期、撤权和两种邮件降级路径均应具备自动测试与可核对审计。

## 6. 完成定义

- Requirements、Design 与 Tasks 分阶段确认并可追溯。
- Admin 与 Provider 的接口契约、密钥轮换、幂等和失败状态具备测试。
- 飞书关联、回调和卡片接口通过鉴权、XSS、CSRF、签名重放与敏感信息审查。
- 两个仓库的 lint、typecheck、test、build 和 CloudBase 代码审查通过。
- production owner canary 与邮件降级演练通过，关闭开关的回退路径验证通过。
