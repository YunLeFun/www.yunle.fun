# 应用反馈与平台支持架构决策

> 状态：已决定
>
> 日期：2026-07-26
>
> 实施状态：尚未实现

## 决策

云乐坊不建设完整即时通讯（IM），也暂不接入外部智能客服或全功能客服 SaaS。

平台基于现有 CloudBase 能力建设一个轻量、异步、结构化的事项引擎，并在产品层严格分成两类：

| 类型                        | 目的                                                                   | 处理者                           | 默认可见范围                             |
| --------------------------- | ---------------------------------------------------------------------- | -------------------------------- | ---------------------------------------- |
| 应用反馈 `app_feedback`     | 用户向某个应用的开发者报告问题、提出建议或咨询使用方法                 | 应用所有者；以后可显式授权维护者 | 提交者、该应用的授权处理者、平台治理人员 |
| 平台工单 `platform_support` | 处理账号、登录、订单、支付、隐私、数据、安全、会员和云币等平台私密问题 | 平台客服人员                     | 提交者、获授权的平台客服人员             |

两类事项共用数据、消息、附件、审计、通知和外部关联等底层能力，但不共用业务队列、处理权限和产品承诺。它是“带状态的异步沟通记录”，不是实时聊天。

## 产品入口与职责

- `www.yunle.fun` 负责发现入口和业务上下文：
  - 应用详情页提供“反馈问题”，携带 `appId` 跳转到支持中心；
  - 用户从通知进入对应事项；
  - 应用所有者在应用管理后台处理应用反馈。
- `play.yunle.fun` 是官方一方应用，也是游戏反馈的上下文入口：
  - 游戏大厅自身使用稳定的 `appId=play`；
  - 每款游戏继续使用自己的稳定 `appId`；
  - “反馈当前游戏”归属于当前游戏，“反馈游戏大厅”才归属于 `play`；
  - 大厅不建设独立反馈库、回复页面或处理后台。
- `support.yunle.fun` 保留现有帮助搜索、公开讨论、私密联系和状态页路由，并新增：
  - 应用反馈提交与用户回复页面；
  - 平台工单提交与回复页面；
  - 登录用户的“我的事项”，按“应用反馈”和“平台工单”分栏。
- 平台客服后台只展示平台工单；不得因为共用引擎而默认看到应用反馈。
- 不能登录的用户继续通过客服邮箱或微信客服求助，不开放匿名站内工单。
- 安全漏洞披露使用独立的 `security@yunle.fun`，不得进入普通反馈、普通工单或公开 GitHub 渠道。

建议的应用反馈入口为：

```text
https://support.yunle.fun/feedback/new?app={appId}
```

`appId` 只是导航上下文。服务端必须重新查询应用及其所有者，不得信任 URL、表单或客户端提交的处理人身份。

事项必须区分反馈对象和提交来源：目标应用决定处理人，来源客户端只用于还原用户场景。用户从游戏大厅启动某款游戏，不会让大厅团队自动成为该游戏反馈的处理人。

## 为什么不做 IM

当前需求是让用户能够说明问题、补充材料、得到处理结果，并保留可追踪记录；它不要求在线状态、输入提示、已读回执、实时会话、坐席分配或多渠道实时接入。

完整 IM 会额外引入连接管理、消息顺序和送达、在线状态、推送、反滥用、内容治理与值班预期。对当前低频、异步的应用反馈和平台支持而言，这些成本不会产生相称价值，反而容易让用户期待即时响应。

因此界面应使用“反馈”“工单”“回复”“状态”等措辞，不使用“在线聊天”“即时客服”等承诺实时性的表述。

## 为什么暂不接入外部客服系统

现有 CloudBase 已提供身份认证、NoSQL 数据库、云函数、私有存储等基础能力，站内也已有 `user_notifications` 通知集合。轻量事项引擎可以直接复用这些能力，避免重复账号、数据同步和供应商锁定。

通用客服产品通常围绕平台统一坐席、排班、SLA 和多渠道会话设计，而应用反馈需要按应用所有权隔离给不同开发者。直接接入腾讯企点、第三方工单或智能客服，会使多租户授权、用户身份映射和隐私边界更复杂。

当前规模下，自建预计更省成本，但这不是永久结论。实施时仍需持续记录存储、函数调用、附件、通知和维护工时，后续用实际总成本重新评估。

若未来接入外部客服，只允许通过适配层承接 `platform_support`；`app_feedback` 继续留在平台内部，避免把第三方开发者反馈权限映射到外部坐席系统。

## GitHub 的角色

站内反馈是用户沟通与隐私审计的来源记录，GitHub Issue 是开发任务，二者不能相互替代。

应用开发者可以：

1. 从反馈创建一个新的 GitHub Issue；创建前编辑并确认脱敏后的公开摘要。
2. 将反馈关联到一个已有 Issue。

第一版的关联记录保存 provider、仓库、Issue 编号、URL、创建人和时间，并从站内单向跳转；另外在审计事件中保存开发者实际确认外发的公开标题与摘要。不得自动复制私密回复、附件、用户身份、账号信息或订单信息，也不做 GitHub 评论双向同步。创建关联后，站内反馈仍然保留并继续独立流转。

公开的产品讨论、可复现的公共缺陷和社区协作仍可直接使用 GitHub Discussions 或 Issues；涉及个人信息的内容必须进入私密反馈或平台工单。

## 权限原则

- 应用反馈第一版只授权应用所有者。
- 数据模型预留显式维护者列表，但授权必须由平台内的应用权限产生。
- 绝不自动把 GitHub 仓库成员、Collaborator 或 Organization 成员视为反馈参与者。
- 应用开发者不得看到平台工单，也不得读取用户账号、订单、支付或安全信息。
- 平台治理人员访问应用反馈必须基于治理职责，并留下审计记录。
- 所有权限由服务端按当前身份和资源状态计算，不能依赖客户端隐藏按钮。

## 通知与邮件

站内通知是默认且主要的通知渠道。通知列表不展示回复正文：

- 平台工单仅提示“有新的工单回复”；
- 应用反馈可展示应用名称和反馈标题，但不展示回复内容；
- 默认不发送邮件；
- 用户可对单个事项主动开启邮件提醒，且只提醒第一条未读回复；
- 邮件中不包含回复正文，也不支持直接回复邮件写入事项。

账号删除、安全告警、支付交易等已有事务邮件不受此决策影响。

## 人工智能的边界

以后可以使用 AI 做帮助文档检索、处理人草稿和会话摘要，但不得在未经人工确认时直接回复用户、修改处理结论或自动关闭事项。

## 第一版不做

- 完整 IM、在线状态、输入提示、已读回执；
- 匿名站内反馈或匿名平台工单；
- 外部客服 SaaS 或智能客服接管；
- GitHub 评论双向同步；
- 自动采集控制台、网络请求、截图或设备详细信息；
- 应用反馈响应 SLA；
- 通过回复邮件更新事项；
- AI 自动回复或自动关闭。

## 影响

正面影响：

- 在现有基础设施上形成低成本、可审计的私密沟通渠道；
- 用户、开发者和平台客服的责任边界清晰；
- 反馈可以关联研发任务，但不会因公开到 GitHub 而泄漏隐私；
- 以后可以按真实需求渐进增加维护者、Webhook 或客服适配器。

需要承担的成本：

- 平台需自行维护授权、状态机、反滥用、附件清理和内容保留任务；
- 支持中心与主站之间需要可靠的跨站登录和跳转；
- 上线前必须更新隐私政策、联系说明和账号删除流程；
- 必须监控实际使用量和维护成本，不能只比较 SaaS 的订阅价格。

## 重新评估条件

出现以下任一持续性信号时，重新评估 IM、外部工单或智能客服，而不是按日历预先建设：

- 用户确实需要在同一次故障处理中进行实时协作；
- 平台出现多个客服坐席，需要排班、路由、升级和明确 SLA；
- 微信、邮件、电话等多渠道统一接入成为刚需；
- 工单量使人工分流成为主要成本；
- 自建系统的维护总成本持续高于合适 SaaS 的采购与迁移成本。
