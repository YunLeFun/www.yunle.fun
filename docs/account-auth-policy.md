# 账号注册与用户名规范

本文是云乐坊账号入口、用户名和错误交互的唯一产品规范。CloudBase Auth、Web 前端、登录页、公开资料服务和相关说明均应以本文为准。

## 登录与自动注册策略

当前账号入口策略：

| 方式                        | 已有账号 | 新用户   | 说明                                                            |
| --------------------------- | -------- | -------- | --------------------------------------------------------------- |
| 中国大陆手机号验证码        | 登录     | 自动注册 | `shouldCreateUser: true`                                        |
| GitHub                      | 登录     | 自动注册 | CloudBase GitHub Provider 开启自动注册                          |
| 邮箱验证码                  | 登录     | 禁止注册 | Provider 自动注册关闭，客户端同时使用 `shouldCreateUser: false` |
| 用户名、手机号或邮箱 + 密码 | 登录     | 不注册   | 密码需在账号安全设置中创建                                      |

登录页必须明确告诉用户上述差异。首次通过手机号或 GitHub 继续即表示创建账号，并适用服务条款和隐私政策；不能把是否创建账号隐藏在验证码或 OAuth 回调之后。

保留独立手机号注册页作为历史链接兼容入口，主入口统一使用“登录 / 注册”。邮箱自动注册不得仅靠隐藏按钮关闭：CloudBase 邮箱 Provider 必须保持启用以支持已有账号登录和登录后的邮箱绑定，同时把 `AutoSignUpWithProviderUser` 明确设为 `FALSE`；客户端调用还必须显式传入 `shouldCreateUser: false`，形成纵深防护。

## 为什么禁止邮箱自动注册

邮箱获取和批量验证成本低，早期直接开放会增加批量注册、一次性邮箱、资源薅取和垃圾内容风险。当前由 CloudBase Provider 的 `AutoSignUpWithProviderUser: FALSE` 强制禁止邮箱自动建号，同时保留 Provider 本身以支持已绑定邮箱登录；公开客户端的 `shouldCreateUser: false` 只是前端侧的第二道约束，不能代替 Provider 策略。

邮箱绑定只能由已登录账号在账号安全设置中发起，通过 `auth.updateUser({ email })` 和验证码完成；绑定后仍是原 UID，不应创建或合并出第二个账号。未绑定邮箱尝试登录时，前端统一使用“该邮箱暂时无法用于登录”的中性提示，引导用户检查输入或先用手机号、GitHub 登录后绑定，不展示“用户不存在”等可用于枚举账号的原始错误。

中性失败文案只能降低公开错误分支的信息泄露，不能完全消除邮箱枚举：直接调用 CloudBase 客户端 SDK 时，“验证码发送成功”和“拒绝发送”本身仍可被区分。彻底隐藏这一差异需要认证平台原生支持，或另行设计受控服务端入口、恒定公开响应、限频和人机校验；在此之前必须把发送限频、异常监控和告警视为发布门禁，不能仅依赖前端文案。

满足以下条件后，才能重新评估是否开放邮箱注册：

- 验证码发送前具备人机校验；
- 按邮箱、IP、设备和风险特征限频，并有发送与验证两层限制；
- 拦截已知一次性邮箱域名，但不误伤企业或自建域名；
- 新账号高价值操作有冷却期或二次风控；
- 有注册转化、验证码成本、异常注册率和封禁申诉监控；
- 服务端仍以唯一约束和原子写入处理并发，不能依赖前端检查。

禁止邮箱自动注册不是完整的防刷方案。手机号和 GitHub 入口仍需限频、异常检测和资源领取风控。

## 唯一的用户名规范

新设置或修改的用户名统一为：

- 正则：`^[a-z][0-9a-z_-]{5,19}$`
- 总长度 6–20 个 ASCII 字符；
- 必须以小写字母开头；
- 其余仅允许小写字母、数字、下划线和连字符；
- 输入值先去除首尾空白并转为小写；
- `tmp_` 开头且符合系统临时用户名格式的值为保留格式，用户不可占用；
- 用户确认正式用户名后不可自行修改。

CloudBase Auth 是用户名唯一性和并发冲突的最终裁决者。前端规则用于即时反馈，不能代替服务端校验。

CloudBase 当前用户态接口实际使用 `^[a-z][0-9a-z_-]{5,24}$`（总长度 6–25），且控制台与公开登录配置 API 不提供自定义正则入口。站内规范因此取其安全子集 6–20：最短长度与 CloudBase 实际约束一致，站内再收紧最大长度。若 CloudBase 后续提供可配置规则，仍需先在测试环境验证五位用户名确实可写入，再讨论把最短长度降到 5。

### 历史账号兼容

规则统一前已经存在的用户名不自动改名。密码登录和 Auth 公开资料快照只为存量账号兼容 3–25 位、大小写不敏感的旧格式；该兼容规则不得用于创建或修改用户名。

## 错误交互

- 用户输入时即时展示字段级格式错误；合法输入不显示错误。
- 提交前再次用同一规范归一化和校验。
- 用户名占用、并发冲突、保留格式和 CloudBase 格式拒绝均回填到用户名输入框下方，并保持弹窗打开。
- 不向用户展示服务端原始正则、错误堆栈或内部错误码，也不为字段错误弹 Toast。
- 设置成功可以使用成功 Toast；无法归类的服务端失败显示“用户名设置失败，请稍后重试”，原始错误只进入受控日志。

邮箱绑定遵循相同原则，但公开登录与已登录设置页的提示粒度不同：

- 公开邮箱登录不得确认邮箱是否存在、是否已注册或绑定；统一提示检查邮箱，并说明首次使用需先通过手机号或 GitHub 登录后绑定。
- 设置页输入当前账号已经绑定的邮箱时，前端直接在邮箱字段提示“该邮箱已绑定当前账号”，不得发送验证码。
- CloudBase 返回 `already_exists` 时，在邮箱字段明确提示“该邮箱已绑定其他账号”，并提供更换邮箱或登录原账号的下一步；不弹字段错误 Toast。
- CloudBase 返回邮箱格式拒绝时回填邮箱字段；验证码错误或过期时回填验证码字段，用户重新输入后清除旧错误。
- 限流、网络和未识别的系统错误使用安全的表单级 Toast，不透传 CloudBase 的 `message`、`helpMessage`、正则或内部配置。
- SDK 错误映射必须同时兼容 `AuthError.status`、`AuthError.code` 和普通对象的 `error` 字段；CloudBase 标准 OAuth 状态通常位于 `status`。

## 短信验证码错误与客服交接

前端只对用户可以自行处理、且不会暴露风控细节的错误提供明确中文提示：

- 手机号格式不正确：提示检查手机号和国家或地区代码；
- 30 秒、1 小时或通用发送频率限制：提示稍后重试；
- 手机号当日发送次数限制：提示次日再试；
- 国家或地区不支持：提示当前仅支持中国大陆手机号；
- 手机号处于短信服务黑名单：提示更换手机号，或通过私密客服协助排查。

签名、模板、套餐余额、服务内部异常和未识别的短信错误统一使用“验证码服务暂时不可用”的兜底提示，不向用户展示腾讯云原始英文、内部错误码或具体风控原因。

需要客服介入时，入口统一跳转到 `https://support.yunle.fun/login-help`。前端只自动携带稳定的产品、来源、错误码和可用的 Request ID，不把手机号、验证码或原始错误写入 URL。支持中心负责让用户确认上下文，并明确以下排查信息：

- 大致发生时间和所在时区；
- 当时执行的操作与阶段，例如登录、注册、发送验证码或校验验证码；
- 页面截图或中文提示；
- 自动带入的 Request ID 和错误码；
- 需要关联账号时提供 UID；需要关联短信记录时，手机号只通过私密客服渠道提供，可先脱敏，确有必要时再补全。

任何情况下都不得要求用户提供密码、短信验证码、Cookie、密钥、完整访问令牌或未经检查的整段日志。

## 变更检查清单

调整账号策略或用户名规范时，必须同时检查：

1. CloudBase 邮箱 Provider 保持 `On: TRUE` 且 `AutoSignUpWithProviderUser: FALSE`，并检查其他 Provider 的自动注册策略和用户名正则；
2. `app/composables/auth/useOtp.ts` 的 `shouldCreateUser`；
3. `app/utils/username.ts` 的新用户名规则与历史兼容规则；
4. 登录页和用户名设置弹窗的说明与字段错误；
5. `cloudfunctions/account-api/profiles.js` 的 Auth 资料快照兼容；
6. 本文与对应自动化测试。

## 发布前门禁

账号策略变更发布前必须全部确认：

1. 在目标 CloudBase 环境重新读取配置，确认邮箱 Provider 为 `On: TRUE`、`AutoSignUpWithProviderUser: FALSE`，手机号和 GitHub 自动注册策略符合上表；仅凭本地代码或历史截图不算通过。
2. 自动化测试覆盖未绑定邮箱登录、邮箱绑定保持原 UID、当前邮箱、邮箱冲突、服务端格式拒绝、验证码错误/过期、限流和未知错误脱敏；同时通过 lint、类型检查和生产构建。
3. 使用专门测试账号完成真实 E2E：全新邮箱不能建号；已绑定邮箱能登录；手机号或 GitHub 账号绑定邮箱后 UID 不变；绑定已被其他账号使用的邮箱得到字段级冲突提示。
4. 确认验证码发送与验证的限频、人机校验或平台风控、异常注册率监控、验证码成本告警和回滚负责人；缺少其中任何一项都应记录风险接受人和补齐期限。
5. 禁止用生产用户邮箱随意触发验证码测试，禁止在日志、截图、URL 或工单中记录验证码、完整令牌和原始 Provider 错误。

以上门禁未完成时可以合并代码，但不得宣称账号策略已完成生产验证，也不得执行生产发布。
