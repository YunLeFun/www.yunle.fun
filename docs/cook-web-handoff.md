# 云食册 iOS 一次性打开网页账号管理

点「管理云乐坊账号」后，网页未登录时建立独立的 CloudBase 网页会话，同账号时沿用现有网页会话。只有现有网页会话属于另一账号时显示确认，取消不修改网页会话。成功后只进入同源固定地址 `/settings?tab=account`。网站的账号限制和敏感操作验证仍生效。

1. iOS 在内存生成随机验证值，系统 Safari 只打开携带其 SHA-256 摘要的交接入口。官网生成独立的随机浏览器证明，放在 host-only、HttpOnly、Secure、SameSite=Strict 的短效 Cookie 中。
2. Safari 回调只向 App 提供 HTTPS 来源和路径。首个站内重定向的路径携带 App 请求摘要和浏览器证明摘要；它随后重定向至官网交接页，页面读取参数后清除地址中的参数。
3. iOS 校验域名、路径和本次请求，再把 App 侧验证值和浏览器摘要通过 HTTPS POST 交给 `sso-ticket`。函数从经 CloudBase 网关核验的非匿名用户解析账号，检查注册表和账号准入。App 的 access token 不进入浏览器或 URL。
4. 交接页从 CloudBase SDK 读取网页登录状态，通过同源接口兑换。服务端通过临时 Cookie 定位浏览器证明，在 `sso_login_codes` 服务端集合中按双重绑定和 120 秒期限原子消费。网页 SDK 会话与启用时的官网会话 Cookie 都参加账号冲突比较。确认只对当时的账号组合有效。仅在需要新网页会话时铸造独立的 CloudBase 登录票据。

`sso_login_codes` 复用既有的服务端权限与清理任务，无需新增集合或开放客户端权限。交接记录保存账号和摘要组成的文档 ID，不保存原始证明、App 的访问令牌或续期令牌。

Mac 上运行的 iOS App 由系统打开默认浏览器，无法依赖应用内 Safari 的重定向回调。能力查询中的 `systemBrowser` 表示官网支持这条路径。Mac 在系统网页认证窗口以 `transport=browser` 开始交接，官网从原入口设置同样的浏览器 Cookie，再通过已关联的 Cook HTTPS 地址仅回传两个摘要。App 校验回调、批准交接后，默认浏览器由现有交接页继续。兑换仍要求对应的 HttpOnly Cookie；没有该 Cookie 的浏览器不能接手。iPhone 和 iPad 继续使用原有重定向。

Android 的账号管理和直装会员结账也使用系统浏览器。首次回调会在 App 内锁定本次申请的浏览器摘要。审批回包丢失后，用户可在原 45 秒有效期内再次使用同一回调。服务端对同一账号、同一申请和同一浏览器的未兑换审批返回原成功结果，保留原到期时间。其他账号、已经兑换或已过期的申请继续被拒绝，浏览器仍只兑换一次。

发布时先更新现有 `sso-ticket`，保留其既有环境变量、权限和 HTTP 路由；再发布官网。在目标环境独立生成 32 字节随机值，分别设成函数的 `COOK_WEB_HANDOFF_INTERNAL_TOKEN` 和官网服务端的 `NUXT_COOK_WEB_HANDOFF_TOKEN`（同一 64 位十六进制值，不进入公开环境变量或客户端）。官网留空时能力查询返回 404，现有 App 继续打开原网页。只有函数就绪后才启用官网变量。

上线验收：分别以未登录、已登录同账号、已登录其他账号的系统 Safari 环境打开；验证切换确认、取消、请求过期、重放和退出 App 后直接打开的地址。关闭能力查询时，旧版 App 和原有网页登录不受影响。
